task_description: |
  Task: perf-001 - Reduce order-list latency by eliminating N+1 database calls

  Instructions:
  Background:
    The Golang backend exposes multiple HTTP endpoints:
    - GET /health
      - Returns a JSON object with service health information.
      - Must return HTTP 200 and a JSON body containing at least: { "status": "ok" }.
    - GET /customers/:id/orders
      - Returns a JSON array of orders for the given customer id.
      - If the customer does not exist, it MUST return an empty array [] with HTTP 200, not an error.
    - GET /customers
      - Returns a JSON array of ALL customers, where each customer includes:
        - "id": customer identifier (matches existing schema).
        - "name": customer name.
        - "orders": array of that customer's recent orders (each order has "id", "customer_id"/"customerID", "amount_cents"/"amountCents").
        - "totalAmount" or "total_amount": aggregated total monetary amount for that customer (sum of all order amounts).

    The current implementation of GET /customers suffers from an N+1 query pattern:
    for N customers, the service issues one query to fetch the customers and then N separate queries
    to fetch orders for each customer. This causes poor latency (>2s) and high database load for larger
    customer sets.

  Goal:
    Redesign and optimize the backend implementation of GET /customers so that it returns the same
    JSON data (customers with embedded orders and totals) but uses O(1) or O(2) database queries total,
    while remaining thread-safe under concurrent access.

  Required behaviors and API schema (MUST match exactly):
    1. GET /health
       - HTTP 200, JSON response body: {"status": "ok"}
    2. GET /customers/:id/orders
       - Existing customer: HTTP 200, JSON array of orders
       - Non-existent customer (ex: /customers/999/orders): HTTP 200, empty array []
       - Each order object MUST contain:
         - "id": order identifier
         - "customer_id" OR "customerID": links to customer
         - "amount_cents" OR "amountCents": order amount in cents (may be negative)
    3. GET /customers
       - HTTP 200, JSON array where EACH customer object contains EXACTLY:
         - "id": customer ID
         - "name": customer name string
         - "orders": array of order objects (same schema as above)
         - "totalAmount" OR "total_amount": integer sum of ALL customer order amounts
       - totalAmount/total_amount MUST equal sum(orders[].amount_cents OR orders[].amountCents)
       - Field casing (camelCase vs snake_case) MUST match repository tests exactly

  Performance requirements (MUST be implemented):
    4. Eliminate N+1 queries in GET /customers:
       - Use at most 2 total DB queries: 1) all customers, 2) all orders for those customers (batched)
       - Response time MUST be ≤500ms (vs base repo >2s)
       - NO per-customer order queries allowed
    5. Thread-safety under concurrent load:
       - 5+ concurrent GET /customers requests must return identical totals (no data races)
       - Shared resources (DB connections, caches) must use proper goroutine synchronization

  Technical requirements (MUST implement all):
    - Dependency inversion:
      - HTTP handlers MUST depend on repository INTERFACES (CustomerRepository, OrderRepository)
      - NO direct sql.DB usage in handlers/services
    - Batch order fetching:
      - Implement GetOrdersByCustomerIDs([]int64) method returning map[customerID][]Order
      - Single SQL query with IN clause or JOIN preferred
    - No global mutable state:
      - Request data must NOT use package-level variables
      - DB pools/clients must be concurrency-safe
    - 3+ files modified minimum:
      - handlers: endpoint logic using interfaces
      - services: business logic calling repositories  
      - repository: interfaces + batch implementations

  Success criteria:
    1. All endpoints return expected HTTP status + JSON schema
    2. GET /customers executes in ≤500ms (batch queries verified)
    3. totals match order sums exactly (including negative amounts)
    4. Concurrent requests return consistent data (no races)
    5. Tests pass 100%: ./run_tests.sh perf-001
    6. At least 3 Go files modified with 30+ lines of changes

  Anti-cheating measures:
    - Tests use live DB data with known totals - hard-coded JSON will fail sum checks
    - Concurrent tests verify race-free behavior under load
    - Timing test (≤500ms) proves N+1 elimination (base repo fails)
    - Field names/casing validated against real test expectations

  File references (modify these exact files):
    - internal/handlers/customers.go - Update handler to use repository interfaces
    - internal/services/customer_service.go - Add batch order fetching logic  
    - internal/repository/customer_repository.go - CustomerRepository interface + impl
    - internal/repository/order_repository.go - OrderRepository + batch GetOrdersByCustomerIDs
    - Any additional service/repository files needed for interfaces

  Implementation workflow:
    1. From clean base repo (git checkout starter-base)
    2. Define CustomerRepository/OrderRepository interfaces  
    3. Implement batch GetOrdersByCustomerIDs using single JOIN/IN query
    4. Refactor handler/service to use interfaces + batch data
    5. Test: ./run_tests.sh perf-001 (must pass all 7 tests)
    6. Generate diff excluding tasks/: git diff --cached -- . ':!tasks/' > task_diff.txt
